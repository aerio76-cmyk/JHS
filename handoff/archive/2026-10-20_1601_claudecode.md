## 3. 1600：`schema.sql` 防重複執行保護
**改動**（`supabase/schema.sql`）：
- 整份用 `begin; … commit;` 包起來，並加上 `@tx-begin`／`@tx-end` 標記註解。不論 SQL Editor 是整份送出還是逐句執行，保護一中止，後面的語句都不會生效。
- `begin` 之後先 `set local search_path = public, extensions`：保護檢查的是 `public.*`，下面建表的 DDL 沒寫 schema 名稱，這行讓兩者看同一個地方。
- **第一個動作**是保護區塊：`public` 底下的 students、subjects、exam_scores、exam_rankings、motivational_quotes、admins 任一存在，**或者 `is_admin()`／`is_super_admin()` 函式還在**（表被手動刪掉、只剩安全強化版函式的情況），就 `raise exception`。中文訊息會列出找到的物件，並指引改用 `supabase/patches/`，要整個重建則參考 README。
- 開頭註解寫明「既有專案不要執行本檔」。

**README**：
- 寫明「`schema.sql` 只能用在全新專案；既有專案只執行 `supabase/patches/`」，以及保護的行為。
- 「資料庫重建」改寫：必須先清空才會通過保護；本機 rebuild 檔**不含 patches**，跑完要另外執行；重建前先下載完整備份。
- 新增提示：中止後如果出現 `current transaction is aborted`，先執行 `rollback;`。
- 「備份與還原」新增：試跑前確認開的是測試專案、兩個專案不要同名；**`main PRODUCTION` 標籤是每個專案預設分支的名稱，不能用來分辨正式或測試**。

**驗證（PGlite，12/12）**：
1. 全新資料庫可以正常套用。
2. 第二次執行（整份送出）會中止，catalog 逐項不變：函式定義、政策、欄位、限制、bucket、資料筆數都比對過。
3. 第二次執行時，**用 PostgreSQL 解析器把檔案切成 50 句逐句送出**：第一個錯誤就是保護中止，其餘 47 句都被 aborted transaction 擋下，資料庫逐項不變。

5. 表被手動刪掉、只剩權限函式：會中止，`is_admin` 維持新版。

7. **中止後如果不送 `rollback`，同一條連線的下一個查詢會得到 `current transaction is aborted`**，送出 `rollback` 後恢復。Supabase SQL Editor 會不會重複使用同一條連線**沒有實測**，所以 README 先加了提示。

## 4. 給使用者的建議（不動本機檔案，需使用者同意）
1. **重新產生本機 `rebuild.local.sql` 時的改法**：rebuild 檔本身有外層 `begin/commit`。如果直接把新版 `schema.sql` 整份貼進去，內層的 `commit` 會**提早結束外層 transaction**；之後的 seed、白名單、學生 insert 只要有一筆失敗，資料庫就會停在「成績全刪、白名單是空的」狀態，家長端進不去。
   - 建議做法：貼進去之前，**刪掉 `schema.sql` 中標有 `@tx-begin` 與 `@tx-end` 的兩行**，保護區塊要保留。保護放在 drop 之後，剛好可以確認清空成功。
   - 同一個 transaction 裡，最後再接上安全 patch，同樣去掉 patch 自己的 `begin/commit`。
   - 目前的 rebuild 檔內嵌的是舊版 schema，**還不受這次改動影響**。
2. **建議在測試專案實測一次**：`schema.sql` 連續執行兩次，然後執行 `select 1;`，看會不會出現 `current transaction is aborted`。如果會，README 的提示已經涵蓋處理方式。
